# Changelog

## 2.0.0 (November 2026)

First release of ReForgeCanvas, a fork of ForgeCanvas 1.3.1. The version jumps to 2.0.0 because defaults change: see "Changed".

Renamed to ReForgeCanvas: package `@tryforge/reforge.canvas`, class `ReForgeCanvas` (`ForgeCanvas` is no longer exported), error enum `ReForgeCanvasError` (was `ForgeCanvasError`), extension name `reforge.canvas`, options type `IReForgeCanvasOptions`, log prefix `[ReForgeCanvas]`. No public export, type or option keeps a ForgeCanvas-only name (a test checks the declarations in `dist/`). Installed from GitHub: `npm i github:Demonic1594/ReForgeCanvas#v2.0.0`.

Every fix below was found in the 1.3.1 source (or in @napi-rs/canvas 1.1.1 and undici 7.30.2, which it uses), reproduced on the 1.3.1 build, and has a test in `test/`. The tests boot a real ForgeScript client (never logged in) and run ForgeScript code through its own compiler and interpreter; only the outside world is stood in for (local HTTP servers, a fake DNS answer, temporary folders). The suite has 84 tests. Run against the 1.3.1 build, 54 of the 67 that apply fail (8 of them because the bot process aborts) and 13 pass (those check behaviour that is kept, such as data URIs, inline SVG and `registerFonts()` from JavaScript); the 17 that test ReForgeCanvas's own options and names are skipped there.

### Security
- **One loader for every source a user can name.** Images (`$loadImage`, `$preloadImage`, `$drawImage`, `$drawImageArea`, `$imageSize`, `$imageBuffer`, `$createFrame`, `$addFrame`), `pattern://` styles (`$fill`, `$stroke`, `$drawRect`, `$drawText`, `$drawProgressBar`), `$newGIFDecoder`, `$registerFont`, `$loadLottieAnimation`, emojis in `$drawText`, and `ImageManager.load`/`tryGet` all go through `src/structures/loader.ts`. @napi-rs/canvas now only receives bytes or a data URI, never a path or a URL.
- **Non-public addresses are blocked**: loopback, private (RFC 1918), carrier-grade NAT, link-local (including `169.254.169.254`), multicast, documentation and reserved ranges, IPv6 unique-local and link-local, and IPv4 inside IPv6 (mapped, NAT64, 6to4). The check runs on IP literals in any spelling the URL parser accepts (`2130706433`, `0x7f000001`, `127.1`, `[::ffff:7f00:1]`), on every redirect, and on the address DNS returns, which is the address the connection then uses.
- **Time limit** for a whole load (redirects and body included), 10 s by default. Before: none in @napi-rs/canvas; undici's 300 s header and 300 s idle-body timeouts in `$newGIFDecoder` and fonts.
- **Size limit**, 10 MiB by default: a larger declared `content-length` is refused before reading, and a body without one is cut off.
- **Redirect cap**, 5 by default (301, 302, 303, 307, 308). Before: 20 in @napi-rs/canvas (only 301 and 302), 20 in undici `fetch`, while `$loadImageOptions` said "unlimited".
- `$loadImageOptions` request options are no longer passed to `http.get` as they are (they could set `socketPath`, `host` or an agent); only `headers` is used, without `Host`.
- **Local reads are off by default** (`files.read`). With a folder set, paths are resolved, `..` cannot leave it, and symbolic links are followed before checking. Before: `$loadImage[x;/any/path]`, `$newGIFDecoder`, `$registerFont` and `$loadLottieAnimation` read any existing file.
- `$loadLottieAnimation`'s `resourcePath`, and each external asset in the animation, must be inside `files.read`. Skia resolves assets as `resourcePath + u + p`; checked with @napi-rs/canvas 1.1.1 that `../` in `u` or `p` reads outside `resourcePath`.
- **Writes are off by default** (`files.write`). `$saveCanvas` and `$saveEncoder` write only inside that folder, and not through a symbolic link at the target (`O_NOFOLLOW` where the OS has it).
- **Fonts**: stylesheet and folder nesting limited (`fonts.maxDepth`, 3) and font files per registration limited (`fonts.maxFiles`, 100). Before, a stylesheet naming itself looped until the server stopped. A stylesheet's `url()` is resolved against the stylesheet's URL and fetched; before, `url(/path/on/disk.ttf)` registered a local file.
- **Cache cap**: automatic entries (emojis, URLs passed to `$imageSize`/`$imageBuffer`, `pattern://` images) are capped per manager (`cache.maxImages`, 500); before, every distinct emoji ID in user text added an image to the global cache for good.
- **Size limits** (`limits`), measured on 1.3.1 first: a 190 KB PNG whose header says 40000x40000, drawn at 500x500, took 3.2 GB and 6 s; encoding a 16000x16000 canvas took 7 s of CPU; 200 frames of 1000x1000 in one GIF took 1.7 GB and 5 s. Now an image's size is read from its header (PNG, JPEG, GIF, WebP, BMP, AVIF, SVG) and refused before decoding over `maxImagePixels` (25 MP); `$createCanvas`, `$resizeCanvas` and `$newGIFEncoder` stop at `maxCanvasPixels` (25 MP); a GIF encoder at `maxGifFrames` (300) and `maxGifPixels` (100 MP); one `$drawText` loads at most `maxEmojisPerText` (50) emoji images, where 1.3.1 fetched all of them at once. Lottie animations (a declared 100000x100000 size and 10^8 frames) and long text (200,000 characters) were measured cheap and get no limit of their own.
- `localhost` and `*.localhost` are refused by name (RFC 6761), whatever the machine's DNS says; `64:ff9b:1::/48` (local-use NAT64, which can map to internal IPv4 addresses) is blocked, found by cross-checking the address list against ipaddr.js. Tests cover `0177.0.0.1`, `0x7f.0.0.1`, `0.0.0.0`, `localhost.`, `[::1]`, IPv6 zone IDs, `100.64.0.0/10`, `fd00::/8` and redirects into private space.
- **Native crashes**: on some arguments @gifsx/gifsx's Rust code panics or tries a huge allocation, and that aborts the whole Node.js process, so one command takes the bot offline and `$try` cannot catch it. Found by the fuzz test (`FUZZ_SEED=1`) and reproduced on 1.3.1: `$newNeuQuant` with 0 colours (index out of bounds), a sample factor of 0, 0.5 or 2^32 (divide by zero) or -1 colours (a 137 GB allocation); `$indexedToRgba` and `$indexedToHex` with a pixel outside the palette or a palette that is not RGB triples; drawing an indexed `frame://` without a palette (`$createFrame[f;indexed://1x1:0]` then `$drawImage[c;frame://f;0;0]`). These arguments are now checked first (`src/structures/native.ts`) and return a normal error. `$newNeuQuant` also takes at most 256 colours, the most a GIF palette holds: 65536 colours took 19 s of CPU on 100,000 pixels, 256 took 62 ms.
- **Generic errors for users**: `This source is not allowed`, `This source is too large`, or the function's own failure text (`Failed to load an image`, `Failed to load the GIF`, ...). The detail goes to the log as `[ReForgeCanvas] $function: CODE detail`. Before, the library's error text was shown, including addresses and paths.

### Changed
- **Upgrading from ForgeCanvas:** `ForgeCanvas` is not exported and there is no alias, so code that does `new ForgeCanvas()` must change to `new ReForgeCanvas()`, and the import from `@tryforge/forge.canvas` to `@tryforge/reforge.canvas`. `ForgeCanvas.components` becomes `ReForgeCanvas.components`; TypeScript imports of `ForgeCanvasError` become `ReForgeCanvasError` (the messages are the same). Commands stay the same.
- Defaults that change behaviour: no local reads, no writes, private addresses blocked, 10 s, 10 MiB, 5 redirects, 25-megapixel canvases and images (see the README's "Who is affected" table for the option that restores each). A refused local path is logged with the option to set (`files: { read: "./assets" }`).
- `files.read: true` and `files.write: true` allow the bot's working folder with guards: only image, font, GIF and Lottie files (images only for writes); never hidden files or folders (`.env`, `.git`), `node_modules`, database files (`*.db`, `*.sqlite`, `-wal`, `-shm`, `-journal`) or a SQLite file renamed to `.png`; no link out of the folder. A one-time warning at start-up recommends a folder of its own.
- `logLevel` option (`silent`, `error`, `warn`, `info`, `debug`, `trace`) and `REFORGECANVAS_LOG_LEVEL`, `info` by default like the other ReForge extensions: one start-up line with the settings in force, and nothing for commands that load images successfully (a refused or failed load is one `warn` line with the reason). Every line ReForgeCanvas prints starts with `[ReForgeCanvas]` (component loading included); `debug` shows each load (host and path, bytes, ms) and cache hits, never query strings, tokens or file contents.
- Wrong options throw a `TypeError` from the constructor, so the bot does not start with a broken setup.
- `$drawImage` and `$drawImageArea` treat a source as a style only when it is a colour, `gradient://` or `pattern://`. Before, any failed image fell back to a style and drew a black rectangle with no error; now the error is returned.
- `registerFonts()` from JavaScript accepts a policy as its third argument. Without one it trusts the caller (local paths anywhere) but uses the network limits.
- `ImageManager` takes a policy (`new ImageManager(policy)`) and has `cache(name, image)` for capped entries; `set()` entries are never evicted.
- ForgeCanvas loaded next to ReForgeCanvas stops the client at start-up with a clear error (from `validateAndInit`, so ForgeScript does not swallow it), whatever the order of the extensions.
- `engines` stays `>=18.17`, like the other ReForge extensions; ForgeScript 2.8 itself needs Node.js 22, and versions below 22 are not tested (CI runs Node 22 and 24, plus ForgeScript 2.5.0).
- `undici` is no longer used (it was imported without being a dependency).
- Added `npm test` (node:test, 84 tests, also passing on ForgeScript 2.5.0): a real ForgeScript client running ForgeScript code; network, files (folders and the guarded `true`), fonts, cache, limits, logging and options; the address check cross-checked against ipaddr.js (dev dependency only); concurrency (100 loads and 200 refusals at once), spam (1000 refusals in a row) and memory (canvases and GIF encoders freed, caches bounded); a seeded fuzz test (`FUZZ_SEED`, `FUZZ_RUNS`, 600 calls by default; run with seeds 1 to 8 and 1337) of every function with hostile arguments, checking no crash, no request or file read where blocked, and catchable errors from the loading functions. `npm run lint` (`tsc --noEmit` and `scripts/lint.js`), and CI on Node 22 and 24 that also checks `dist/` and `metadata/` are up to date.
- Performance (same machine, 3 runs of 200): loading an 800x250 PNG from a local server 0.92 to 1.17 ms in 1.3.1, 1.43 to 1.54 ms now (the address and header checks); drawing a cached image 0.99 to 1.16 ms in 1.3.1, 0.22 ms now (1.3.1 decoded it again on every use); a typical card 6.94 to 7.34 ms in 1.3.1, 6.37 to 6.86 ms now.

### Fixed
- `$indexedToRgba` and `$indexedToHex` failed with `Failed to convert napi value` when `transparent` (or, for `$indexedToHex`, `alwaysAlpha` or `allowShort`) was left empty. With no transparent index, gifsx still returns alpha 0 for every pixel; that is gifsx's behaviour and is kept.
- `$saveCanvas` always failed with `image/png is not valid format` (it passed a MIME type where the format name was expected).
- `$imageSize` and `$imageBuffer` with a URL or path failed when no image had been loaded before in the same command.
- `registerFonts()` stopped at the first missing font when logging was off (`return` instead of `continue`), and font folders were registered without waiting.
- `$imageSize[preload://name]` and `$imageBuffer[var;preload://name]` never found the image (the name was looked up with `preload://` still on it).
- A cached image (`images://`, `preload://`) was decoded again each time it was drawn.
- The build failed with @napi-rs/canvas 1.1 typings (`createPattern` may return `null`); a `null` pattern is now an error.
